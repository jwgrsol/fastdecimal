❯ Day.js — 가장 정확한 선례. 개인 개발자(iamkun)가 혼자 시작한 프로젝트인데, 전략이 fastdecimal과 판박이입니다: 당시 지배적이던 Moment.js(무겁고, mutable하고, tree-shaking 불가)를 겨냥해 **"Moment와 거의 같은 API, 2KB, 더 빠름"**을 내걸었죠. Moment 사용자가 import만 바꾸면 대부분 동작하는 호환 전략으로 기존 사용자층을 흡수했고, 지금 주간 다운로드 수천만으로 Moment를 실질 대체했습니다. Moment 팀이 스스로 "새 프로젝트엔 우리 대신 다른 걸 쓰라"고 공식 선언하며 유지보수 모드로 들어간 것까지, 방금 얘기한 lodash 역학 그대로예요. 회사 없이, "레거시 호환 + 명확한 우위 하나(크기)"만으로 개인이 해낸 겁니다. 어떻게 다른 프로젝트가 내 라이브러리를 사용하도록 설득해야해?

핵심 원리부터: **설득은 말이 아니라 "상대의 리스크를 대신 제거해주는 것"**입니다. 다른 프로젝트의 메인테이너 입장에서 의존성 교체는 이득(성능)은 작아 보이고 리스크(미묘한 버그, 유지보수 불확실성)는 커 보이는 거래예요. 채택 전략은 전부 이 비대칭을 뒤집는 작업입니다. 순서대로 정리할게요.

0단계 — 설득 자료가 먼저 (지금 해야 할 것)

접근하기 전에 상대가 확인할 세 가지를 갖춰야 합니다. 메인테이너는 반드시 이걸 검증하러 옵니다:

- 재현 가능한 벤치마크 — "빠르다"가 아니라 "당신이 직접 돌려볼 수 있는 스크립트 + 결과 표". 피연산자 크기별(작은 수/큰 수), 연산별로. esbuild가 README 첫 화면에 벤치마크 그래프를 박은 이유입니다.
- 호환성 증명 — "big.js 자체 테스트 47,456개 100% 통과"는 이미 있으니, CI 배지로 보이게 만들기.
- 신뢰 신호 — v1.0.0(0.x는 "불안정"으로 읽힘), 의존성 0개, 타입 내장, 라이선스 명확, 이슈 응답 흔적. 개인 프로젝트일수록 "이 사람이 내년에도 있을까"를 이걸로 판단합니다.

1단계 — 타깃 선정: 아무나가 아니라 "아픈 사람"부터

npm에서 big.js/bignumber.js의 역의존(dependents)을 훑어서 이런 프로젝트를 고릅니다:

- 활발히 유지되고 (죽은 프로젝트의 채택은 무의미)
- 성능이나 번들 크기가 실제 고민인 곳 — 이슈 트래커에 "bundle size", "slow", "bignumber performance" 같은 이슈가 있는 프로젝트가 최우선. 이미 아픈 사람에게 진통제를 파는 게 건강한 사람 설득보다 백배 쉽습니다.
- 중소 규모부터 — 대형 프로젝트(예: ethers)는 보수적이라 초기엔 문전박대당합니다. 중소 프로젝트 서너 개의 채택 실적을 만든 뒤에 큰 곳으로 가는 겁니다. es-toolkit도 Storybook 이전에 작은 채택들이 먼저였어요.  
  2단계 — 접근 방식: 요청하지 말고, 일을 다 해서 가져가라

순서가 중요합니다:

1. 이슈부터 연다 (PR 먼저 던지는 건 무례로 읽힐 수 있음): "이 프로젝트가 big.js를 X 경로에서 쓰는데, drop-in 호환 대체로 바꾸면 이런 이득이 있다. 관심 있으면 PR을 준비하겠다."
2. 숫자는 상대의 맥락으로 — "우리 벤치마크에서 3배"가 아니라 "당신 프로젝트의 이 함수를 당신 테스트 데이터로 돌리면 이만큼". 상대 저장소를 클론해서 직접 측정한 before/after를 가져가는 겁니다. 이게 이 전략의 핵심 차별점이에요 — 메인테이너가 해야 할 검증 노동을 당신이 대신 끝내주는 것.
3. PR은 최소 diff — import 한 줄 변경 + 상대의 기존 테스트 전부 통과. "리스크가 없음"을 diff 크기 자체가 증명하게.
4. 거절도 자산 — 거절당하면 이유를 물어보세요. "0.x라서", "실적이 없어서" 같은 답이 다음 할 일 목록이 됩니다.
